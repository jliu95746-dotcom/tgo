## 分配行为

- 在原人工领取/转交权限复核之后、写入分配状态之前，读取当前规则。自动分配重新查询当前人员与负载，并刷新会话内 ORM 缓存；原模型选择仍有效时优先保留，没有再请求模型。
- 最终人员必须属于当前项目，账户启用、接待启用、未暂停、未删除，且为人工角色。保留原在线状态策略：不把 `offline` 直接当作永久禁止接待，原模型仍可选择符合其他条件的离线人员。
- 有容量上限时，PostgreSQL 使用按项目/人员编号生成的事务级 advisory lock（应用主动申请的数据库锁）尝试占用名额，争用时立即返回，不在持有访客锁时等待另一分配完成。随后重新读取人员，并检查当前项目内的开放会话数；本次同一会话不重复占一个名额。
- 当前人员行使用共享锁和 `SKIP LOCKED`；已有未提交人员写入时跳过该人员。自动分配可继续尝试其他当前候选；全部不可用时保留等待，不把旧选择带入历史。
- 指定目标不可用、已满或被另一分配占用时，返回失败并回滚，不悄悄分给其他人。既有权限、访客/会话版本和受控错误处理继续保留。
- 上限为空的现有配置保持允许并行，不建立容量争用锁；没有规则的既有行为保持。同一会话重新分配不会重复计算自己。
- 最终人员发生变化时，清除不再适用的模型原文、理由和评分，保存受控原因；实际尝试的模型、提示词仍保留，没有调用第二次 AI。

名额占用和人员行锁由所属事务提交或回滚释放，没有增加持久化名额表、后台补偿任务或数据库迁移。SQLite 仅验证逻辑，不作为并发安全证据；并发结论来自下面的真实 PostgreSQL 连接。
