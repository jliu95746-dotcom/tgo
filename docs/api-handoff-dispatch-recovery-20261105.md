## 行为和恢复边界

人工转接接受后先保存停止 AI 的状态，原来在随后的分配过程被中断时，既没有队列，也没有最终回执。严格幂等重试只能报告结果未知，客户可能一直等待。

本批复用现有人工请求 JSON 元数据和排队处理器，不新增服务、表模型或迁移：

1. 接受新请求时保存 version=1 的接待绑定，包含平台、服务状态、模式、AI 开关与当前会话身份。该标记与停止 AI 的状态在同一事务提交。
2. 现有员工消息恢复循环增加人工请求扫描。仅处理更新已超过 **300 秒**、仍 pending、有已知版本标记且未删除的请求；每轮最多 20 条，参数限定 1～50，使用请求编号游标翻页并在末尾回绕，避免一个持续失败项挡住后面的请求。
3. 按企业、项目、访客、相关资源的顺序核对并加锁；访客与请求使用 `SKIP LOCKED`，多个工作进程不会同时恢复同一项。每条请求独立提交，失败回滚后保留恢复标记供后续重试。
4. 已经提交有效人工会话或有效队列的请求，直接保存其回执，避免重复分配。仍未分配且接待绑定未变的请求，原子补齐会话、既有等待队列和回执，由现有队列机制继续接待。
5. 恢复本身不再次请求 AI，不发送原人工转接提示。恢复入队后，既有排队处理器仍可按当前配置执行一次新的正常分配；这与重新播放中断阶段的外部调用不同。
6. 已恢复 AI、切换辅助模式、注销访客、删除/停用渠道、归档项目、结束/更换会话或队列失效时，不重新排队，不覆盖当前访客状态；请求保存 cancelled 回执。没有标记的历史请求和未知版本标记保留原状态供其所属版本或人工处理，不推测旧动作并自动重放。
7. 慢 AI 返回时如果恢复进程已经完成请求，原调用读取已保存回执，不把恢复成功的请求改成 rejected。正常完成的内联请求移除恢复标记。
8. 恢复新建会话时，确保其创建时间严格晚于同一访客上一会话，避免数据库时间相等时随机 UUID 排序把旧会话当成最新会话。

恢复回执的 `notification_status` 固定为 **unknown**。本批证明业务接待状态可恢复，不声称客户提示、客服红点、IM 成员变更或微信消息已经实际送达。排队刷新沿用既有提交后通知机制，其进程间可靠送达仍属后续工作。
