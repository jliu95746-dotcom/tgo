## 实现与边界

- 原失败处理直接按版本编号读取记录，没有再次限定企业。真实 PostgreSQL 合成用例证实：另一企业传入目标版本及已知批次时，主处理虽然拒绝，失败回写却可能把目标标为失败。现在 SQL 同时限定版本、来源企业、当前 `processing` 状态及匹配的处理批次，并锁定该版本；找不到匹配项就不写入。
- 失败回写不再完整解析一次已经损坏的快照。有效批次仍可记录自身失败；缺失、损坏或不匹配的批次不授予写权限。模型失败、旧任务、非处理状态及已删除原资料分别验证，原生效内容和版本号保持。
- 来源读取仍按原顺序锁定原资料、来源和版本；刷新后复核来源范围没有变化、原资料属于该知识库、版本仍绑定该来源。来源与原资料知识库不一致的文件、QA、网站三种情况均拒绝，不继续发布到错误范围。
- 明确模型选择、版本状态及治理参数类型，复用既有 Literal 和枚举进行真实校验；不增加 cast 或忽略诊断来绕过检查。原有两处 ORM 行类型转换保留，冗余转换移除。
- 三个可空字段改为显式 `Field(default=None, ...)`，使类型检查正确识别构造默认值。**9 份版本 Schema、4 份默认载荷、43 路径和 55 组路由依赖完整相同**；没有修改调用方字段或扩大允许值。
- 普通文件、QA 与网站的既有发布规则保持。准备阶段增加知识库不可用和替换文件元数据缺失时的明确拒绝；其余准备逻辑、正常结果处理及发布规则经过限定范围的执行结构对照，枚举构造按原实际值归一化。没有重新引入普通文件已取消的审核和渠道选项。

本批 **5 文件：3 份服务源码、1 份 Schema、1 份新测试**；另外 **83 份运行源码字节内容保持**。没有依赖、ORM、迁移、服务器配置或其他服务修改。21 项数据库测试与专用夹具围绕同一版本状态机，经评估保留在同一测试文件，没有另建测试框架。

## 独立数据库与原始失败

- 只使用本机已有固定镜像，Linux PostgreSQL **16.14**、pgvector **0.8.5**，256 MB/1 CPU，仅监听回环地址。五个专用测试库均使用合成资料；新测试要求指定前缀、回环地址和初始无公共业务表，并在专用随机 schema 中运行。
- 初始化辅助脚本首次把临时 Unix socket 服务的就绪当成最终服务就绪，下一条数据库命令退出 2；核验同一容器仍运行后，改用 TCP 就绪检查并沿用原完整编号恢复，没有重复创建容器或重跑未知业务动作。
- 第一轮类型检查还发现两处适配器缺泛型注解和查询结果退化为 Base，分别通过明确类型与真实模型实例验证解决；目标规范检查发现长行/无用导入，按原值排版并移除。没有削弱断言，原失败记录保留。
- 最终结束时，五库均无私有 schema、公共业务行数均为 0；模型、向量和新版本专项库无公共业务表，两个基础专项库各有 10 张空结构。按完整容器编号、任务标签和实际端口核验后清理其容器及匿名卷，原 PostgreSQL、Redis、WuKongIM 编号保持且 healthy。
- 原生统一验证脚本仍检查不存在的 `app`，退出 1；其编译 PASS 不计证据，实际另对 `src` 完整检查。PR 摘要脚本仍仅有标题、退出 1，提交范围按五文件允许清单和实际差异核对。
