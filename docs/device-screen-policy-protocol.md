# Windows 单窗口屏幕策略协议 v1

实现位置：Go 客户端 `internal/protocol/screen_policy.go`、`internal/tools/screen_policy.go` 与 `internal/transport/screen_policy.go`；Python 控制服务 `app/schemas/device_screen_policy.py` 与 `app/services/device_screen_policy.py`。

本协议用于同一已认证 TCP 连接内的授权交集与确认。**协商成功不等于业务测试通过、员工启用或正式 MCP 执行。** 控制服务已有独立的内部 HTTP 持久发布/撤销接口，尚未接入公网 API 和管理页面；正式 MCP 发现与调用继续屏蔽 `screen_*`，不要通过放开通用工具或复用 `fs_read` 策略绕过。

## 本机授权与可见停止

客户端默认关闭屏幕能力。使用者在设备本机选择窗口、程序及有限输入范围，或者在本机配置明确窗口。客户区位置/尺寸、DPI、实际进程及创建时间、前台、交互桌面和响应性都需要继续匹配。有效本机授权生成随机 32 位小写十六进制 `grant_id`，它是不可重放的本机授权实例编号，不包含 HWND、程序路径、标题、进程身份或屏幕绝对坐标。

本机状态窗口显示真实目标与停止入口；优先放到目标窗口外侧，没有空余位置则以不抢焦点的任务栏入口显示。按住 `Esc`、停止按钮、关闭状态窗口或退出客户端均可结束。停止后不能通过重发策略恢复，需设备使用者重新核对。重连后的第二次认证也使旧授权失效。

本机请求了屏幕模式但初始化失败时，不回退开放原文件/命令工具。已有发布读取策略仍仅允许 `fs_read`，优先于屏幕请求并停止本机屏幕授权；服务器不能以屏幕协商扩大既有文件权限。

## `screen/status`

无参数，只接受空参数或空对象。有效授权返回：

| 字段 | 说明 |
|---|---|
| `protocol_version` | 固定整数 `1` |
| `active` | 当前授权可用性；不能由在线状态代替 |
| `grant_id` | 当前本机授权编号，32 位小写十六进制 |
| `width` / `height` / `dpi` | 客户区像素尺寸与本机窗口 DPI |
| `allow_click` / `allow_text` | 本机是否明确允许该能力 |
| `click_regions` | 本机客户区内矩形列表，最多 16 个；每项 `x/y/width/height` |
| `max_actions` / `used_actions` | 本机批准的输入总上限与本实例已尝试的点击/输入次数 |

不可用时只给固定版本、`active: false` 和无权限的零值，不返回旧授权或旧几何。元数据中不返回私有窗口身份。截图仍返回已授权窗口的实际内容，不能把“不传身份字段”误解为画面已脱敏。

## `screen/policy/apply`

服务端请求以下字段，未知字段、缺失权限、`null` 权限或非整数坐标均拒绝：

| 字段 | 约束 |
|---|---|
| `protocol_version` | 固定 `1` |
| `revision` | 整数 1～2147483647，不能回退；同版本必须同摘要 |
| `grant_id` | 必须是当前仍有效的本机授权实例 |
| `max_actions` | 1～50，不能超本机上限，也必须大于已经使用的次数 |
| `allow_click` / `allow_text` | 明确布尔值，不能超出本机许可 |
| `click_regions` | 不允许点击时为空；允许点击时至少一个，每个矩形必须包含在某一本机批准矩形内 |
| `digest` | 以下规范计算的 64 位小写十六进制 SHA-256 |

客户端确认返回 `protocol_version/revision/grant_id/digest`，全部精确匹配才记为同一连接已确认。旧客户端不支持方法或返回超时/错误时保持未确认。

失败更新，包括无效 JSON 形状，清除之前已应用策略及旧截图凭据。同版本同摘要重复确认不重置计数、不增加额度；新版本使旧 `view_id` 失效。策略扩大也不能越过本机授权，上限耗尽或本机停止后不能重开。读取策略已存在时不能改成屏幕执行。

服务器协商同时核对连接实例、当前管理器中的连接对象与当前期望策略；对象替换、文件策略变化、迟到确认或摘要/编号不符不登记成功。调用方必须持有原设备生命周期锁，不能把协商函数当成公开授权入口。

## 摘要规则

依次用 UTF-8 编码下列行，每一行末尾都有 `\n`，包括最后一行：

```text
tgo-screen-policy-v1
<revision>
<grant_id>
<max_actions>
<allow_click: true 或 false>
<allow_text: true 或 false>
<click_regions 数量>
<x>,<y>,<width>,<height>
...按请求原顺序逐行列出矩形
```

区域顺序属于摘要，不能在一端重新排序。样例：版本 1、编号为 32 个 `a`、上限 5、两个输入权限均 false、区域数 0，摘要为 `3e1772db3e2809fb5dddd5b25fa4f4bf3051622c3059bdc707d506b40a1826d2`。Go/Python 均有固定向量验证。

## 工具调用与截图隔离

本机屏幕模式尚未确认时只发现 `screen_stop`。确认后只发现 `screen_screenshot`、`screen_stop` 及本策略批准的 `screen_click/screen_type_text`，文件和命令工具不会混入。点击同时受到服务端策略矩形和本机矩形约束。

每次输入使用刚取得的一次性 `view_id`。截图、授权范围或窗口变化后不能继续使用旧凭据；每次输入前再次获取同一窗口画面并比对。普通文本限原生 `Edit`，不支持密码、浏览器字段、换行或快捷键。成功输入只说明送达，不证明业务保存、提交或查单完成。

截图使用当前客户端程序的隔离子进程。父进程通过私有匿名管道传入一次性编号与先前核验的窗口快照；子进程重新核对窗口，仅绘制该窗口并裁切客户区。身份快照不写到命令行、网络结果或文件。子进程不加载账号令牌、配置或网络服务。

`PrintWindow` 是可能阻塞的系统调用，因此只在子进程内执行；父进程设置 2 秒期限，超时/取消时终止并等待该自有进程退出，不能在绘制仍使用 GDI 资源时由主进程提前释放它们。输出仍受 PNG 1 MiB、约 400 万像素限制，没有桌面截屏回退。前台检查还使用有界的无副作用窗口响应探测。实际支持范围须逐软件验证，API 返回成功或工具存在不能代替画面/业务核验。[Microsoft PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)

## 验证边界与后续接入

目前已有两语言契约/读取策略回归、独立真实 Windows 客户端与合成本机 TCP 对端的认证/确认/PNG/点击/重连验证，以及明确停驻的自有截图子进程的实际超时/退出验证。阻塞子进程仅存在于测试可执行程序，发布客户端不带停驻测试模式。

这些不代替真实 Windows 客户端与 Device Control HTTP/MCP/TCP 的完整服务链路。API/Web 授权管理和显式文件/屏幕模式切换已接入，见下文；同连接业务测试报告、员工/工作流固定摘要与签名会话绑定、有限查询场景及结果检查仍需继续，再按能力开放 MCP。多显示器、混合 DPI、真实物理停止/锁屏及其他业务软件分别验收；录制回放继续依赖这些门槛。

## 内部 HTTP 管理与持久化

以下为 Device Control 的 `/v1` 内部路由。管理端通过现有 tgo-api 的 `/v1/device-control/devices/{device_id}/` 同名后缀代理访问；五项新增代理均要求企业管理员，企业范围从当前员工身份取得。API 沿用现有 HTTP 客户端和短期服务 JWT，严格核对上游返回的企业及设备归属，不把原始异常载荷暴露给页面。`tgo-ai` 身份不能发布或撤销。接口不接受客户端上传“验证通过”状态，也不提供任意工具执行入口。

| 路由 | 作用 |
|---|---|
| `GET /v1/devices/{device_id}/screen-grant` | 查询当前连接实例及本机不含窗口身份的授权范围；离线不返回旧编号 |
| `GET /v1/devices/{device_id}/screen-policy` | 读取已保存策略，重新查询本机有效性；停止、范围变小或连接改变后降为待确认 |
| `PUT /v1/devices/{device_id}/screen-policy` | 提交 `expected_policy_revision`、当前 `connection_instance_id/grant_id` 和明确范围；版本/摘要由服务端生成 |
| `POST /v1/devices/{device_id}/screen-policy/revoke` | 提交期望版本；保留递增版本和撤销时间，并关闭精确绑定的连接 |
| `POST /v1/devices/{device_id}/read-policy/revoke` | 提交期望文件策略版本；保存停用与撤销时间、递增版本并断开原文件连接，保留目录及历史记录 |

迁移 `0011_device_screen_policy` 新增 `dc_device_screen_policies`，保存期望范围、版本/摘要、原连接实例和撤销历史，不保存截图、输入正文、窗口身份或生效回执。`pending/active/revoked` 分别表示待本连接确认、已确认和已撤销；本阶段 `verified` 固定为 `false`。`active` 只说明范围协商通过，不能用于员工业务启用。

先锁设备行，再核对版本和文件模式冲突；设备行同时保护首次发布时“策略行还不存在”的竞争。持久提交后重新锁定并核对当前版本，才向原连接发协议确认。文件发布也沿相同设备行锁检查有效屏幕策略，两种模式不能同时发布。迁移 `0012_device_read_revocation` 为文件策略增加 `enabled/revoked_at`，旧记录默认继续启用。文件撤销清除旧测试与连接确认；停用策略不会在重连时自动下发，也不能继续进行旧测试。切换时先明确撤销，再在设备端重新授权和连接；屏幕发布只接受当前新授权，不靠删除文件记录绕过。重新发布文件策略从保留的版本继续递增。存在文件撤销历史时，迁移降级明确拒绝丢弃历史。

撤销保留版本，重复撤销需携带当前版本；提交失败或取消也清除旧确认并关闭原连接，不误断替换连接。服务重启只恢复期望记录，不从数据库自动恢复本机授权、回执或业务测试状态。非空策略表的降级会明确拒绝，不能为回滚丢弃撤销历史。

持久化验证在随机本机 PostgreSQL schema 内依次执行 12 个实际迁移的升级函数，覆盖独立会话竞争、屏幕/文件互斥、ASGI HTTP 发布/撤销、重新读库、文件撤销后重新授权并切换屏幕、再撤销并发布下一版文件策略，以及旧行回填、空表降升与非空降级拒绝，结束逐一检查自建 schema 已删除。TCP 回复为合成夹具、HTTP 企业身份在数据库专项中由依赖注入提供；另有使用临时签名密钥的真实 JWT 边界测试。不能把它们合并成真实网络服务或真实设备验收。

## 管理端授权范围

本机入口为 `/ai/device-control` → 设备卡片“管理授权范围”。文件和屏幕分别展示待确认、设备已确认范围、已撤销等状态。撤销需要在同一弹窗明确确认，保留历史并断开使用原授权的连接，不会自动切换模式。没有新本机授权时提示重新启动客户端并选窗。

屏幕输入权限默认关闭；用户可明确选择普通文本和有限区域点击，并在本机批准区域内进一步缩小坐标和输入次数。页面、网关和 Device Control 各自验证归属、版本及范围；错误或无法重新核对时禁止写入。账号/设备改变及弹窗关闭后，旧异步响应不能覆盖新上下文。页面沿用现有浅色/深色样式及中文文案。

“设备已确认范围”只代表当前连接确认了权限，业务验证仍未通过。页面明确显示该限制，`verified` 继续固定为 `false`，不能据此启用 AI 员工的屏幕执行能力。
