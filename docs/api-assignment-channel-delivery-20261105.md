## 具体实现

新增 `api_assignment_channel_deliveries`，主键沿用所属分配历史编号，保存项目、访客、接待会话、目标客服、频道操作和可选接待提示。通过 Alembic `0082_assignment_channel_delivery` 创建，父修订为 `0081_agent_knowledge_catalogs`，修订编号为 32 字符；当前迁移链只有这个新 head。公开接口、消息类型和既有 IM 客户端保持。

1. 分配历史、会话/排队状态、数据库频道成员和同步意图在同一事务保存。`auto_commit=False` 只暂存，不自行提交或调用 IM；调用方回滚时全部回滚。调用方提交后，现有员工后台恢复循环处理持久化记录；自动提交路径还会立即尝试。
2. 成员操作与接待提示分别保存状态。成员操作为 `pending/unknown/done/skipped`；先提交本次尝试和 unknown，再调用既有 IM 客户端。成员增删按既有接口的幂等语义恢复，不能借重试重复创建业务分配。
3. 手动关闭/转交与自动分配共用成员同步执行器。同一项目/访客使用 PostgreSQL 会话级 advisory lock 串行化外部操作，专用的一条连接同时承担短数据库阶段和互斥；HTTP 等待期间没有业务行锁或未提交的业务事务。SQLite 的进程内锁只服务本机单进程测试，不充当生产多实例证据。
4. 每步重新读取当前会话、项目、访客、平台和人员资格；不删除当前客服，不把旧目标重新加入。添加等待期间接待变化或人员停用时，补偿移除刚加入的旧目标。新的操作包括历史已软删除成员，以便清理更早的在途操作；取消保持传播，并释放传输互斥。
5. 接待提示保留原类型和载荷，固定编号 `assignment-{history_id}`。发送前复核当前接待、员工及原操作权限快照，先提交 sending 再 HTTP；权限快照不保存原令牌。发送结果未知时超过 30 秒查询同编号历史，核对编号、频道、频道类型、发送者和完整载荷；不把查不到当作重发依据。
6. IM 停用时保留尚未尝试的意图。恢复每轮 20 项，参数限制为 1～50；失败更新冷却时间，使后续工作可以继续。成员结果和提示结果分别处理；跳过过时记录不代表已尝试的外部动作从未发生，恢复周期不构成送达时限承诺。

接待状态或权限在最后检查后、HTTP 已发出期间变化时，不能撤回在途请求。当前接待检查和成员补偿减少旧状态影响，但不构成所有正式渠道、进程和任意并发交错均已验收的结论。
