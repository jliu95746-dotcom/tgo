# 员工详情归属契约与知识评审恢复

## 目标与已确认缺口

接续 4.2.277 的实际 Ego 云端验收。知识能力状态、员工测试问题与知识评审出现 404；错误为“未找到当前企业的 AI 员工”。API 路由已注册，当前员工在列表可见，不能将问题归结为缺少前端页面或直接跳过归属检查。

源码表明 `tgo-api.agent_knowledge_cases._agent` 要求远端员工编号、企业编号同时匹配，而 `tgo-ai.AgentResponse/AgentWithDetails` 未声明 `project_id`，实际详情序列化会丢弃 ORM 已有的企业编号。本批补齐服务端响应契约，保留缺失/异企业/异员工的原拒绝逻辑。

## 实施和验收

1. 先验证基础/详情响应 JSON 与实际注册详情路由的输出；响应企业编号必须来自服务端员工记录，不从请求参数补值，缺失/空值/错误 UUID 拒绝。
2. 在 AI 响应模型声明已有的必填企业编号，核对 API、Web、CLI 的消费者；不新增数据库字段或迁移，不修改客户记录或当前接待员工。
3. 运行 AI 响应/员工及 API 归属/目录/能力/评审回归、完整默认工程和同步检查；以隔离候选及真实 HTTP 验证响应与原网关校验，再提交推送及限定发布。
4. 发布后在原 Ego 空间 0/p1 的云端登录态实际检查测试问题、能力状态和评审恢复，不自动通过评审、切换员工或把旧报告当成本轮真实模型验收。

原 D1～D7、官方微信、多模态和 G0～G5 全范围保持；真实订单/物流继续暂缓，安卓员工客户端取消。工程检查、合成契约、正式页面和真实业务分别记载。

## 实现和当前检查

- 已在 `AgentResponse` 声明必填 UUID `project_id`，详情、列表、创建和更新的响应继承同一契约，值由原 ORM 员工记录提供。`AgentCreate/AgentUpdate` 没有增加此输入字段，不用请求企业编号补值，不修改 API 目录的归属校验。
- 原实现新增十项响应与实际注册路由的序列化测试均失败，修正后通过；覆盖基础/详情 JSON、缺失/空值/非法 UUID，以及请求企业不同仍保留记录原始归属。路由测试的服务返回是隔离替身，未把该用例当作数据库过滤或鉴权验收。
- AI 组合最终 **97 passed / 60 warnings**；API 目录、能力、评审与原角色路由组合 **54 passed / 17 warnings**，包含新增七类缺失/错归属的原拒绝逻辑和正确 actor/project 转交。API 业务源码没有修改。六个旧知识准备测试原来用同步 Mock 数据库，无法等待现有授权及执行引用查询；只补齐这两个测试依赖，并保留流/非流路径和真实执行门禁回归，不降低运行时校验。
- 云端无网络、只读、1 CPU/1536 MiB 容器依次完成两个服务的默认 `mypy app`：AI **112 errors / 40 files / 319 source files**，与上批逐项比较新增 0；API **559 errors / 108 files / 623 source files**，本批 API 业务源码未改。完整语法检查通过，完整 AI/API Flake8 仍失败；四个修改源码/测试文件相对原源码新增 lint 为 0。
- 新字段已执行 schema 同步检查并人工追踪：网关知识目录直接使用 AI client 的原 JSON 核对归属，原公开网关员工 DTO/前端展示投影及 CLI 不将额外字段作为授权依据，不需要新增输入或修改权限。无 SQL 模型变化，不需要迁移；无流格式变化。完整工程失败没有写成通过。
- 线上只读核对确认当前 AI 响应模型未声明企业编号，API/AI 当前镜像及健康状态已核对。后续限定发布将实际恢复备份，验证真实 AI 详情/列表返回和异企业拒绝，再在原 Ego 空间验收。
