# 独立岗位编辑后的草稿刷新恢复

## 真实缺口与目标

沿用 Ego 空间 0/p1，在云端刷新并继续已有草稿 `3c1a3132-fd70-4f15-85d6-ca65deb8e719`，再次确认原员工恢复接口返回 HTTP 409：`员工配置尚未保存，请恢复原草稿后重试`。此草稿的员工和独立岗位版本 2 已保存；不能把它当作创建失败重新生成员工，也不能覆盖后来修改的岗位。

前一批解决的是同会话步骤导航，见[云端向导及六题试聊](employee-onboarding-cloud-20261105.md)。本批补刷新后的服务端恢复：同一版本与原保存内容一致时，读取同一个员工；实际配置已变化时仍拒绝旧内容覆盖。

## 实现范围

仅修改 AI 所有者服务 `app/services/agent_drafts.py`，沿用原接口和响应模型，API/Web 无需升级，无 SQL 表或迁移变化：

- GET 原保存记录不再因后来独立编辑或移除岗位而丢失员工关联。只有岗位仍归属本草稿时提供该归属元信息；独立编辑后不伪装成草稿仍拥有该岗位。
- 同修订 POST 必须先验证原命令摘要，再重读实际员工职责、设置及关联资源逐项核对。相同则只返回原保存结果，不执行创建、更新或岗位写入。返回的岗位选择是摘要验证过的原保存请求，不作为当前接待权限证明。
- 新修订仍先检查草稿对岗位的归属，拒绝覆盖独立修改；实际员工设置已变、跨企业/创建人、同版本内容冲突、已删除员工均保留拒绝。原员工的接待状态不因重试改变，响应始终 `can_enable=false`；正式启用继续使用当前岗位、资料及评审的独立核验。

影响分析已完成：AI 为唯一修改服务，API 是原 HTTP 消费者；原 API 对回执身份、修订和岗位选择的严格校验不变。项目技能分析使用 Git Bash 的 LF 副本，保持原逻辑；本机状态脚本核实基础设施和服务均未启动，Docker 引擎管道不存在。因此未启动可能续办历史任务的本机应用，实际数据库和候选 HTTP 改用服务器内部隔离网络，不连接生产数据库或模型供应商。
