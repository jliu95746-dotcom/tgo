## 问题和实现

`POST /v1/chat/turns/inbound` 原来按位置调用 `chat_completion(body, db, credentials)`，而实际函数第二个参数已是 `Request`，导致数据库和身份参数错位。`media-ready` 又调用同一个入口，因此也受影响。

本次在两个 HTTP 入口注入实际 `Request`，内部调用改用明确参数名，将原数据库会话、Bearer 凭据和请求中的 `X-SaaS-Service-Token` 传到原聊天处理函数。没有用服务器配置替换调用者凭据，没有跳过访客或内部渠道身份验证；缺失服务头明确传入 `None`，不再落入 FastAPI `Header` 默认描述对象。

轮次入库继续使用原聊天入口、真实权限解析和 `TurnStore`；图片/语音就绪继续校验原始消息、当前持有者和文件归属。强制非流式接收回执的原有行为保持，重复消息不新增片段，媒体回填只推进一次版本。后台 worker 的调用已使用具名参数、实际 Request 和受控服务身份，本阶段没有修改它。
