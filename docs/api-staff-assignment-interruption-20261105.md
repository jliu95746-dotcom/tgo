## 问题与实现

原分配过程在等待外部 AI 时已经持有访客写锁、更新排队尝试或创建会话。取消和人工领取可能被阻塞，返回的旧分配结果也可能覆盖等待期间发生的有效操作。本批沿用既有分配服务，分成只读预检与最终写入两个阶段。

1. 新增 `staff_assignment_binding.py`，保存项目、平台、访客服务模式及当前会话的不可变快照。消息计数、更新时间和昵称等不参与比较，正常新消息不会使分配永远失效。
2. AI 等待前只读取接待规则、排队项与接待快照，不申请项目/访客业务行锁，不提前写入排队尝试或分配会话；读取及调用使用 `no_autoflush`，避免查询触发尚未提交对象的隐式写入。
3. 等待后重新核对企业权益，按既有顺序锁定项目、访客、相关会话与排队项。取消、领取、过期、重新排队、平台停用、项目归档或接待模式变化时拒绝旧决定。只有最终仍有效的尝试才记录排队次数并创建或复用会话。
4. 分配配置在模型返回后先无锁复核，最终写入前再按供应商、规则的顺序加锁复核。两次之间撤销配置也不能应用旧结果；不重复调用模型。
5. 显式传入的会话必须属于同一项目和访客，且仍为 OPEN。错误或已关闭会话不能悄悄替换成另一会话。
6. 后台排队重试保留当前 `assist` 且 AI 已禁用的人工辅助状态，旧队列中的开关无论为 true 或 false 均不能把它改回其他模式；没有扩大自动回复权限。明确的人工转交语义保持原样。
7. 人工转接服务先提交已接受请求、停止 AI 的状态和标签，再进入慢分配，使其他连接在等待期间可以读到人工请求。`transfer_to_staff(auto_commit=False)` 仍由调用方决定提交或回滚，不在该函数内偷偷提交。

涉及六份运行源码：`staff_assignment_binding.py`、`staff_assignment_guard.py`、`staff_assignment_response.py`、`queue_lifecycle.py`、`transfer_service.py`、`human_handoff_service.py`。内部结果增加配置快照，无公开 API 字段、表模型、迁移、页面、依赖或长期规则变更。

## 未完成与下一步
