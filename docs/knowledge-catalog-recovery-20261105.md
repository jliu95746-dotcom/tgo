# 企业测试问题的未知保存恢复

## 原目标和实际缺口

接续 D1 配置与恢复验收，Ego 沿用用户指定的空间 0/p1，实际访问云端员工页。模拟保存网络失败前先拦截该页测试问题目录的写请求，不向服务器转发；未知提示和原请求重试按钮出现，关闭并重新打开模拟员工试聊后，两者消失。此次拦截一次、实际配置写入零次；诊断 fetch 包装已恢复。

源码中的 load 每次清空全部目录状态，丢弃同一身份、同一员工的 pending 保存；切换员工也存在同类丢失。现有 API 按原请求键保存不可变版本、支持返回原回执，服务端无需新增写接口或数据库迁移。

## 本批实施和验收条件

1. 保留同一管理员登录内各员工尚未确认的原请求及冻结问题，切换员工不混用草稿；身份、企业或角色变化时清除全部恢复状态。
2. 重开先做只读查询。只有请求键、原管理员、员工、修订和六个问题均匹配才确认保存；其余情况保留原请求，用户明确重试时发送相同键和原正文，不自动重新提交。
3. 当前版本被其他修改取代时保留原未知操作；原回执明确非当前后提示冲突并要求重新读取，不把旧成功覆盖成新当前配置。
4. 新增恢复/切换/迟到/错误回执回归；保留原目录、试聊、评审及身份测试，执行完整前端检查，再限定提交、推送和 Web 发布，在原 Ego 页面复核。

恢复问题正文仅保存在当前登录页面内存，不新增本地持久化、不宣称浏览器刷新后保留。数据库中的正式版本和历史保留；该内存恢复改进不替代 D1-A 的启用原请求持久恢复，未完成的原业务路径与 D1～D7/G0～G5 保持。真实订单/物流继续暂缓，安卓客户端取消。

## 实现与专项检查

- store 只保留尚未确认的命令，按当前登录身份和员工隔离；离开时在途请求也按未知结果保存，迟到响应不能改动另一个员工。重开先 GET，只有员工、原管理员、请求键、修订和原六题一致才恢复成功；不一致、查询失败或回执非法仍冻结原问题，显式重试复用原正文和请求键。明确成功、旧回执或拒绝后清理该员工恢复缓存，身份变化清理全部。
