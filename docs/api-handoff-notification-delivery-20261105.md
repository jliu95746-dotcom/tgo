## 实现与状态含义

原人工转接在保存接待状态后直接发送提示。发送前退出、发送结果不明确，或 IM 已接受而本地回执提交失败时，没有独立的后续处理记录。本批使用现有人工请求元数据保存 version=1 通知意图，复用现有 IM 客户端与后台恢复循环，没有新增服务、表模型、迁移、接口或页面。

| 内部状态 | 含义 | 自动处理 |
|---|---|---|
| pending | 已保存，尚未领取发送 | IM 可用且接待仍有效时领取 |
| sending | 已持久化领取，外部结果尚未保存 | 超过 30 秒后查历史，不重复发送 |
| sent | 实际发送函数验证了同编号回执，或历史记录完整匹配 | 返回现有确认 |
| unknown | 外部发送或查询不能确认 | 继续受控查询，保留人工复核边界 |
| skipped | 停止自动处理过时或不可访问的通知 | 不发送、不继续查历史 |

API 沿用 `notification_status=submitted/unknown`：只有 sent 映射 submitted，其余均为 unknown。submitted 表示 IM 接受或历史确认，不代表客户已阅读，也不证明微信渠道已收到。skipped 若发生在一次发送尝试后，也不代表消息从未送出。

- 通知以现有逻辑人工请求为单位保存一份不可变意图，固定编号 `handoff-{request_id}`。重复调用不覆盖旧载荷或再发同一提示。没有已知意图的历史未知结果不自动补写或重放；未知版本也不由本版本处理。
- 新接待回执与待发送意图在同一事务保存。先持久化 sending 和尝试次数，再释放数据库锁进入 HTTP；查询后仅更新对应意图的回执状态，保留其他业务元数据。
- 发送前重新核对项目、访客、平台、接待模式、当前会话和队列。已分配场景还检查客服账号及归属；访客注销、模式变化、会话/排队失效或客服停用时停止过时提示。原请求已进入 HTTP 后无法撤回，不将检查前有效理解为整个网络等待期间状态永远不变。
- 结果未知时使用既有 `get_message_by_client_msg_no(..., raise_on_error=True)`，比对消息编号、渠道、渠道类型、发送者和完整载荷。没有记录、查询失败、响应不完整或内容冲突都保留 unknown，不把“没查到”当作可以再发的依据。
- IM 停用期间保留 pending；启用后可处理尚未尝试的通知。访客访问已注销等渠道边界失效后，停止新的历史查询。
- 人工分配中断恢复在保存接待回执时一并保存新通知意图；现有员工恢复循环增加独立通知游标，每轮 20 条、范围 1～50，末尾回绕。
- 资料刷新与主要提示分别处理，刷新函数即使抛异常，也不会取消已经确认的提示回执。非严格来源请求也保存接待回执；旧记录的既有未知状态不被推断为“尚未发送”。
