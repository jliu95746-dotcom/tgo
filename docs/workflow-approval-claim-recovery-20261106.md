## 实际缺陷与修改

旧镜像在隔离 PostgreSQL、Redis、实际 Workflow HTTP、独立 Worker 与受控员工验证接口中完成七组检查，但另一组实际失败：审批已批准，Worker 已领取、尚未开始后继步骤时强制终止进程；重启和重复队列投递后仍为 running，原批准记录与运行之间的恢复关联已清除，后台只巡检 pending_resume，无法继续。原失败保留在忽略目录 `.tmp/approval-runtime-20261106/check-03-status.json`，不将其改写为成功。

本批修改仅涉及 Workflow：

1. 领取批准任务后保留审批关联，固定本次执行段时间；完成或失败时再清除关联。恢复令牌在原子领取前生成，旧进程不能通过重新读取运行记录取得新进程的执行归属。
2. 后继节点开始前，先在现有节点执行表提交不含输入、输出正文的 running 记录。结束时更新同一记录，不新增第二条执行结果。
3. 新增每 60 秒的恢复巡检。使用执行任务配置的硬时限及原有 120 秒宽限，默认至少等待 480 秒；时限缺失、非法或溢出时拒绝自动回收。
4. 只有后继节点尚未开始，才能回到原 pending_resume，继续使用原批准与加密检查点。出现任何后继执行记录时停止自动恢复，保留检查点、显示待核验错误并撤销旧执行归属，避免重复操作。
5. 节点开始、结束、整段结束、下一次审批及内部售后待办创建均核对执行归属。通用事件超时清理不再抢先删除上述批准恢复记录；终止后原隐私清理继续执行。连续审批、撤权、取消、并发和重复队列行为保留回归。

没有新增模型、表结构、迁移、公开接口字段或前端页面。尚未开始的恢复与已经开始的核验是两种结果，不宣称已实现所有外部业务的自动恢复。

只读检查确认正式 Worker 当前使用 solo。超过配置时限只用于判断恢复巡检候选，不能单独证明旧进程已经终止；自动恢复还必须核对持久化开始记录，并在旧进程返回时检查原执行归属。活进程暂停后恢复的跨进程竞争仍需另行验收，不能由本批强制终止进程或单元测试代替。
