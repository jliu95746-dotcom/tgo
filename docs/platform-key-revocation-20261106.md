## 问题与修复

原平台密钥字段允许空值，但访客数据、私有渠道及附件检查直接把它交给 SecretStr、字符串比较或编码。密钥清空时会出现类型/编码异常，部分空白状态还会生成无效访问快照，不能稳定返回既有 401 拒绝。

附件初始授权还有一个独立问题：取得访客访问快照后，旧代码从可变的 Platform 对象计算密钥摘要。若平台密钥在两步间变化，附件身份可能采用变化后的密钥，而不是原始访问快照。单独加载固定起点的附件实现、重放该交接用例，已复现摘要错误。

本次实现：

1. 统一读取平台密钥，拒绝缺失、非字符串、空白或无法编码的值；返回有效原值，保留空格和字符的严格匹配，不以字符串转换或裁剪生成新密钥。
2. 使用明确的 UTF-8 字节进行现有恒定时间比较；无效密钥或无法编码的期望值返回不匹配，继续按原权限错误拒绝。
3. 网页访客和私有渠道都在创建访问快照前检查密钥；私有渠道继续要求原服务令牌，失效状态下不创建或修改访客。
4. 聊天操作在 await 前后、响应头和正文发送前继续复查原授权；平台密钥无效时受控拒绝，不释放结果或附件字节。
5. 附件摘要从原访客凭证快照生成，后续与当前有效密钥摘要核对；不会因平台对象变化而取得新的授权。员工访问仍使用独立权限生命周期，合法员工读取自己的附件保持有效。

这是当前授权状态的核对，未新增密钥历史、轮换版本或永久撤销记录；不承诺恢复完全相同的旧密钥后，所有旧能力仍永久失效。
